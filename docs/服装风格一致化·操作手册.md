# 服装风格一致化 · 操作手册

> 把某件装备改造成和"基准件"（比如全身紧身衣）**同一个风格**的通用流程。
> 不针对具体服装 —— 换成手套、靴子、外套、护甲，步骤完全一样。
> 每一条"坑"都是实际踩过的，附了症状和判据。

---

## 0. 一句话原则

> **先确认"用户在看哪个文件"，再动手。**
>
> 这个项目 80% 的返工都来自这一件事没做。

---

## 1. 四条铁律

| # | 铁律 | 原因 |
|---|---|---|
| 1 | **动手前先确认目标文件** | 改错文件 = 全部白干，而且用户看不到任何变化 |
| 2 | **改前备份到 `_archive\<日期>_<说明>\`** | 改坏能退 |
| 3 | **改后必须回读验证** | 写入 API 返回成功 ≠ 真的写进去了（字符串写入就经常静默失败） |
| 4 | **不要凭感觉判断"有没有变化"，要量** | "我觉得生效了"是本项目第二大的坑 |

## 2. 文件地图 —— 到底该改哪个？

### 2.1 三个关键位置

| 路径 | 角色 |
|---|---|
| `CalienteTools\BodySlide\ShapeData\<项目>\<件>.nif` | **BS 源**。BodySlide 的 Build 输入；**Outfit Studio 打开的就是这个** |
| `CalienteTools\BodySlide\ShapeData\<项目>\<件>.osd` | 滑块定义。**二进制**，按"形状名 + 逐顶点权重"绑定 |
| `meshes\<路径>\<件>_0.nif` / `_1.nif` | **构建产物**。低/高体重两个版本，游戏实际读取的 |

### 2.2 判据：走不走 Build？

```
走 BodySlide Build  ──►  只改 ShapeData (BS 源)
                         改 mesh 没用，Build 会覆盖掉
                     
直接用现成 mesh     ──►  改 meshes\...\_0.nif 和 _1.nif
```

> **血泪实例**：某次改了三轮 mesh，用户那边毫无变化 —— 因为他用的是 BodySlide 工作流，
> 而 Outfit Studio 里显示的是 ShapeData。两边是**不同文件**。

### 2.3 三步确认法（必做）

在动手前，用这三个信息交叉确认目标文件：

1. **BodySlide 里 "Outfit/Body" 下拉框**选的是什么名字
2. **Outfit Studio 标题栏**显示的文件名
3. **Outfit Studio 右侧网格列表**里的**形状名**

然后读目标 NIF，看它里面的形状名/顶点数是否和 3 对得上。

```
对不上 → 你找错文件了，继续找
对得上 → 再动手
```

> 形状名会暴露真相。例如用户说"我换了手套"，如果 NIF 里的形状叫 `Gloves_low`，
> 而你去改的是 mesh 里那个叫 `Glove` 的形状 —— 那就不是一个东西。

### 2.4 常见陷阱

- **ShapeData 和构建产物可以有完全不同的形状名和顶点数**（用户换过源文件之后尤其如此）
- **ShapeData 里的形状和 mesh 里的形状可以不是同一个**（作者手工改过其中一个）
- 构建产物 `_0` 和 `_1` **不一定几何相同**：滑块在低/高体重都拉到同一端时才会相同。
  判断方法：逐顶点比对，差值 0 就是同一份。

## 3. 风格一致化 = 三层

改造顺序固定：**几何 → 材质 → 贴图**。上层没对齐就调下层，等于白调。

### 3.1 第一层：几何接续（有没有断层）

量**在接缝处的 z 范围重叠量**：

```python
# 相邻两件，各自的 z 范围
grip = min(A.z_max, B.z_max) - max(A.z_min, B.z_min)
grip > 0  →  接上了
grip <= 0 →  有断层
```

**注意事项**
- 不要用"看起来够不够"来判断。0.65 单位也可能够用，7 单位也可能不够 —— **要结合关节活动幅度判断**，但首先要有重叠。
- 一个网格文件里有**多个形状**时（比如 鞋面 + 鞋底 + 袜套），要**逐个形状**查，不能只看整体包围盒。
- 低/高体重两版（`_0`/`_1`）**都要查**。常见 bug：`_1` 少做了几个形状 → 只有高体重下有断层。

### 3.2 第二层：材质参数（**10 项，不是 3 项**）

**这是最容易做不干净的一层。**

#### 完整清单

| # | 属性 | 说明 |
|---|---|---|
| 1 | `Glossiness` | 高光锐度 |
| 2 | `Shader_Type` | **0=默认 / 1=环境贴图 / 2=发光 / 3=视差 …** 见下 |
| 3 | `Env_Map_Scale` | 环境反射强度缩放 |
| 4 | `Spec_Str` | 高光强度 |
| 5 | **`Spec_Color`** | **高光颜色** ← 最容易漏 |
| 6 | `Soft_Lighting` | 柔光 |
| 7 | `Shader_Flags_1` | 位标志，含 `Environment_Mapping` 等 |
| 8 | `Shader_Flags_2` | 位标志，含 `EnvMap` / `GlowMap` 等 |
| 9 | **`EnvMap` 贴图** | 反射球（cubemap） |
| 10 | **`EnvMask` 贴图** | 反射遮罩 |

#### 血泪点 ①：只看 `Spec_Str` 会漏掉 `Spec_Color`

```
基准件 Spec_Color = (0.529, 0.436, 0.619)   暗梅紫 -> 高级胶质感
目标件 Spec_Color = (1.000, 1.000, 1.000)   纯白   -> 银器感 / 廉价塑料感
```

两者 `Spec_Str` 都是 1.0，**只比强度会以为一致了**。

#### 血泪点 ②：`Shader_Type=0` 在预览里"看不出反射"

```
Type=0  默认着色器   -> 不采样环境贴图 -> 在无动态光源的预览里 = 发哑/发闷
Type=1  环境贴图     -> 采样 EnvMap     -> 预览里能看到反射 = 亮
```

**判据**：如果两个件在预览里一个亮一个哑，先看 `Shader_Type`。

#### 血泪点 ③：`EnvMap` 不同 = 风格不同

即使 8 项数值全一致，**换了 cubemap 也会完全变味**。
基准件用 `mat\standardcubemap_1.dds`，目标件用 `mat\standardcubemap_9.dds` → 反射图案不一样。

#### 对比方法：**全属性 dump，不要挑**

```python
def dump(shape):
    p = shape.shader.properties
    d = {}
    for k in dir(p):
        if k.startswith('_'):        # 跳过 bufSize / logger 之类
            continue
        try:
            v = getattr(p, k)
        except Exception:
            continue
        if callable(v):
            continue
        if hasattr(v, '__len__') and not isinstance(v, str):
            v = tuple(round(float(x), 4) for x in v)
        elif isinstance(v, float):
            v = round(v, 4)
        d[k] = v
    return d

diff = [k for k in set(dump(a)) | set(dump(b)) if dump(a).get(k) != dump(b).get(k)]
```

**先跑这个，再决定改什么。** 自己挑几项"看起来相关"的来比，一定会漏。

> 本项目最快的定位就是靠这个全量 dump —— 前面靠猜连错两次。

#### 关于 `Eff` 叠加层

很多服装有 **两个几何完全重叠的形状**：主体 + `Eff`（发光层）。
`Eff` 通常是 `Type=2 / Spec_Color=(0,0,0)`，**它盖在上面会把高光抹掉**。
查的时候**两个都要查**，并确认基准件对应的 `Eff` 是什么参数。

### 3.3 第三层：贴图

#### 3.3.1 换网格 = 换 UV（必然）

用户换掉 NIF 之后，**UV 布局一定变了**，旧贴图必然错位。

**先量，别猜**：

```python
# 在目标网格的顶点 UV 上，采样它当前引用的贴图
px = clip(uv[:,0] * (W-1)); py = clip(uv[:,1] * (H-1))
samp = texture[py, px]
# 看中位数/均值
```

判据：

| 采样结果 | 含义 |
|---|---|
| 中位 ≈ 0（纯黑） | 落在空白区。**如果基准件也是纯黑，这反而是对的** |
| 中位 ≈ (128,128,255) 的均值 170 | 平坦法线，正常 |
| 中位很高/杂乱 | UV 错位，采样到了别的部件的内容 |

> **反例也是收获**：有次换了手套，判定"UV 肯定错位了"，
> 结果顶点采样显示新手套刚好落在旧贴图的**纯黑空白区** ——
> 而基准件（胶衣）也是纯黑 —— **歪打正着，底色天生一致**。
> **不量就发现不了这种好事，只会瞎改。**

#### 3.3.2 颜色对齐：量基准件的**实际采样值**，不要目测

```
基准件在它自己 UV 上的采样中位 = 0     (纯黑)
目标件在它自己 UV 上的采样中位 = 28    (灰)
-> 目标件亮一个层级
```

**做法**：把目标件的漫反射目标区刷成基准件的那个**数值**（不是"调暗一点"）。

#### 3.3.3 测量方法：**顶点采样 > 三角形填充**

UV 足迹测量有两条路：

| 方法 | 结果 |
|---|---|
| 顶点泼溅 + 形态学膨胀 | **会涂花**（只打到顶点，膨胀成方块） |
| 三角形栅格化填充 | **会过填**（大三角形撑满外接矩形） |
| **顶点采样贴图值** | ✅ **最可靠**，直接用 |

要判断"贴图和 UV 对不对得上"，**采顶点就够了**，不需要精确的覆盖面积。

#### 3.3.4 遮罩类贴图（EnvMask / AlphaMask）

基准件遮罩全白 = 全反射；目标件遮罩中位 25 = 反射被压掉 90% → **目标件会哑一大截**。

**对齐方法**：把目标件的遮罩刷成和基准件同样的值。

#### 3.3.5 DDS 输出规范（必须全部保持）

```
尺寸      保持一致（不要擅自 2K→4K）
mip 层数  保持一致
DXGI 格式 保持一致（BC7_UNORM=98 / BC7_UNORM_SRGB=99，在字节偏移 128）
alpha     必须原样保留
```

**`Image.open(p).convert('RGB')` 会毁掉 alpha 通道** —— 漫反射/遮罩类贴图全程用 `RGBA`。
症状：出现反光斑块、颜色不对称、透明区变成实心。

**texconv 必须显式给 `-m <mips>`**：

```
-m 12   ✓
-m 0    ✗  FAILED [mipmaps] (80070057)
(省略)  ✗  同上
```

## 5. 验证清单（改完逐项打勾）

- [ ] **几何**：与备份逐顶点比对 `verts` / `uvs` / `tris`，确认没被改动（如果只改材质）
- [ ] **节点/形状数**：与备份一致
- [ ] **形状名**：与备份一致
- [ ] **材质**：回读 8 项数值 + `Spec_Color`，容差 `< 1e-3`
- [ ] **贴图路径**：回读 `sh.textures`，确认是预期值
- [ ] **贴图文件**：尺寸 / mip / DXGI / alpha 全部与原文件一致
- [ ] **贴图内容**：目标通道的指标符合预期（非黑区比例 / 中位亮度）
- [ ] **接续**：相邻件 z 重叠量 > 0（逐形状、`_0` 和 `_1` 都查）
- [ ] **文件大小**：若有变化要能解释（PyNifly 重写会丢几字节填充，属正常）

|---|---|---|---|

| 11 | **以为"没重叠就是有缝"** | 过度设计 | 先量重叠量，再判断 |

| 16 | **只信"写入 API 返回成功"** | 以为改好了 | **存档 → 重新 `NifFile()` 打开 → 再回读** 才算验证 |

## 7. 工具能力边界（很重要，决定方案可行性）

| 操作 | PyNifly | 二进制原地改 |
|---|---|---|
| 改标量（float/int），如 `Glossiness` / `Shader_Type` / `Env_Map_Scale` / `Spec_Str` / `Shader_Flags_*` | ✅ `write_properties()` | ✅ |
| 改数组，如 `Spec_Color` | ✅ `write_properties()` | ✅ |
| **改贴图路径（任意长度）** | ✅ **`set_texture(slot, path)`** | ⚠️ 变长需重建字符串表 |
| **新增**贴图槽位（原本没有） | ✅ **`set_texture(slot, path)`** | ⚠️ 需改贴图集块 + 字符串表 |
| 改顶点/UV/三角形 | ❌ **只读**（`verts`/`uvs`/`normals`/`tris` 无 setter） | ⚠️ 需重写形状块 |
| 改蒙皮权重 `bone_*` | ⚠️ 属性只读，但有 `setShapeWeights()` / `set_skin_to_bone_xform()` | — |
| 删除形状 | ❌ | ⚠️ 需重映射全文件块索引，**不建议** |

> **可写属性**（`fset` 非空）：`name` / `properties` / `flags` / `has_alpha_property` /
> `transform` / `controller` / `segment_file` / `shaderflags1`
> **只读属性**：`verts` / `uvs` / `normals` / `tris` / `textures` / `bone_*` / `shader` / `parent`

### 7.1 ⚠️ `textures` 的静默失败陷阱（最容易误判的一处）

`NiShape.textures` / `NiShader.textures` 返回的是**一个缓存字典**，不是活视图：

```python
# ✗ 错误写法 —— 不报错，但【什么都没写进文件】
sh.textures['EnvMap'] = r'textures\mat\cube.dds'

# 而且同对象回读会骗你！
sh.textures['EnvMap']          # -> 显示你刚设的值（读的是缓存）
n.save()
# 只有重新 NifFile() 打开，才发现根本没改
```

**根因**（`pyn/pynifly.py` 的 `textures` 属性）：读进缓存后 `return self._textures`，
真正落盘只能走 DLL 的 `setShaderTextureSlot`。

**正确写法**：

```python
sh.set_texture('EnvMap',  r'textures\sse_silent_code\mat\standardcubemap_1.dds')
sh.set_texture('EnvMask', r'textures\sse_silent_code\suittex\tex_body_alphamask2.dds')
n.save()
```

**可用槽位名**：`Diffuse` `Normal` `Glow` `RimLighting` `SoftLighting` `HeightMap`
`Greyscale` `EnvMap` `EnvMask` `FacegenDetail` `InnerLayer` `Specular` `RootMaterialPath`

**防御措施（已对本地副本施行）**：把 `textures` 改成返回只读视图，
赋值会**立刻抛 `TypeError`** 而不是静默失败：

```python
from types import MappingProxyType
...
return MappingProxyType(self._textures)
```

（库内部一律用 `self._textures[...]` 直接填缓存，外部只有只读断言，
所以这个改动**不会破坏库自身**。备份见 `_archive\2026-10-01_PyNifly_textures只读补丁\`）

### 配套要点

- **写标量必配 `sh.shader.write_properties()`，然后 `n.save()`**（`save()` 不接受参数）
- **写贴图必用 `sh.set_texture(slot, path)`** —— 见 §7.1，字典赋值会静默失败
- **验证必须"存档 → 重新 `NifFile()` 打开 → 再回读"** ✗
  同一对象上回读会读到缓存，**不能作为验证依据**
- **PyNifly 重写文件会丢几字节填充**（文件变小几字节），**属正常**，
  但要靠 §5 的逐顶点比对证明几何没坏
- **`.osd` 是二进制**，头部能看到形状名 + 滑块名，后面是逐顶点权重数据。
  形状一换就得重新生成，脚本无法代劳
- **等长替换仍可用**于简单场景（`standardcubemap_9.dds` ↔ `standardcubemap_1.dds`，都是 21 字符），
  但既然 `set_texture()` 能用，**优先用它**（不用管长度）

### 7.2 ⚠️ MO2 虚拟文件系统的"启动快照"特性

**MO2 的 VFS 是在 MO2 启动时建立的。** 在 MO2 运行期间新增的文件，
**不会被已经运行的工具看到** —— 包括从 MO2 启动的 BodySlide / Outfit Studio。

**症状**：文件明明在磁盘上、NIF 引用也正确，工具却画 `No Image` 占位图。

```powershell
# 在静默代码 mod 下新建了一个贴图
<mod>\textures\[J3] Latex\glv.dds

# MO2 已在运行 -> 它的 VFS 快照里没有这个文件
# BodySlide 通过 VFS 找 -> 找不到 -> No Image
```

**对策：完全退出 MO2 再重新启动**（不是只重启 BodySlide ✗），然后从 MO2 里启动工具 ✓

**诊断顺序**（按这个顺序排除，能少走弯路）：

```
1. 文件在磁盘上吗？            -> Get-ChildItem / os.path.exists
2. NIF 里的引用对吗？          -> sh.textures（只读，直接读即可）
3. DDS 头部合法吗？            -> magic / 尺寸 / mips / DXGI / 数据长度
4. 以上全对 -> 那就是 VFS 快照   -> 重启 MO2
```

## 9. 最后：判断力比工具更重要

本项目返工的根因**不是工具不行，是流程跳步**：

| 跳过的一步 | 代价 |
|---|---|
| 没确认用户在看哪个文件 | 三轮白干 |
| 没量"到底有没有问题"就开方案 | 提了 3 个方案，2 个不需要 |
| 挑几个属性对比而不是全量 | 多花两轮才定位到 `Spec_Color` |

**记住这三句：**

1. **先问"你看的是哪个文件"**
2. **先量，再改**
3. **全量对比，不要挑**
