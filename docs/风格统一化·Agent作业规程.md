# 风格统一化 · Agent 作业规程

> 这份文档不是给 mod 用户看的，是给 **执行任务的 agent** 看的。
> 它记录的不是"某个套装怎么改"，而是**改任何套装都适用的流程、纠错与查证方法**。
>
> 配套阅读：`服装风格一致化·操作手册.md`（面向操作者的具体步骤与命令）

---

## 0. 一句话原则

**风格统一化 = 先分组，再对齐；分组错了，越对齐越糟。**

把所有部件拉到同一组参数，结果不是"统一"，而是**全体塑料化**。这是本工程反复验证过的结论。

---

## 1. 核心概念：风格组

### 1.1 一个套装不是一个整体

同一套服装里的部件，按**形态**和**材质语义**天然分成几组：

| 组 | 形态特征 | 材质语义 | 典型成员 |
|---|---|---|---|
| **紧身组** | 贴合曲面、顶点密度高、随身体变形 | 乳胶 / 氨纶 / 紧身衣 | 本体、手套、袜子、鞋、手部覆盖 |
| **垂坠组** | 大平面、褶皱自由、不贴身 | 布料 / 纱 / 绸 | 裙、披风、外套下摆、面纱、腰带 |
| **硬件组** | 小而密、金属语义 | 金属 / 硬塑 | 链条、扣件、环、饰钉 |
| **排除组** | 不是这件衣服 | 皮肤 / 参考体 | 身体网格、手部皮肤、虚拟碰撞体 |

### 1.2 两条铁律

**铁律 A：组内必须一致。**
同组部件用**完全相同的**参数集合（含反射球、高光色、标志位），否则同一件衣服上会出现两种质感。

**铁律 B：组间必须区分。**
紧身组与垂坠组必须**参数不同**。把垂坠件当紧身件处理 → 硬邦邦的高光 → 塑料感。
反过来，把紧身件按布料压暗 → 失去乳胶的湿润感。

### 1.3 如何判定某件属于哪组

```
看形态   : 顶点数 / z 跨度 / 是否贴身（与身体网格的距离）
看 UV    : 大块连续 vs 细长条带
看命名   : 名字里常带语义线索（cloak / belt / skirt / glove ...），但不可作为唯一依据 ✗
看引用   : 它用的是哪张贴图，以及那张贴图还有谁在用
```

**判定有疑问时**：把它单独列出来问，不要猜。

## 2. 材质的三层杠杆

改材质有三种粒度的手段，**作用域和风险完全不同**：

| 层 | 作用域 | 是否共享 | 风险 | 说明 |
|---|---|---|---|---|
| **着色器标量**<br>（光泽度、高光强度、反射强度、高光色…）| **单个形状** | 不共享 ✓ | 低 | 最安全，逐形状精确控制 |
| **着色器标志位**<br>（各向异性、边缘光、软光照…）| **单个形状** | 不共享 ✓ | 低 | 同上，但**是否被渲染器响应需要实测** |
| **贴图**<br>（漫反射、法线、遮罩、高光…）| **整个文件** | **共享** ✗ | **高** | 一改就会影响所有引用它的部件 |

### 铁律 C：改贴图之前，先列出"还有谁在用"

```
对每个目标部件：
  枚举它的每一个贴图槽 -> 对每张贴图，反查整个 mod 里所有引用者
  -> 如果引用者超出了本次的作用域，就必须【新建一份副本】而不是原地改
```

**这条铁律是本工程损失最大的一处**：一张被两组共用的贴图被原地修改，导致另一组被静默改坏。

### 铁律 D：外形细节不要凭空生成

**不要用程序化噪声去"画"有语义的表面细节**（褶皱、板件分缝、划痕、缝线）。

原因：
- 程序化图案与模型的**实际形态对不上**（关节在哪、板件边界在哪，噪声不知道）
- 结果要么像贴纸，要么像裂开，要么整体糊掉

**可以做**：低频、无方向语义的**变化**（让反射/高光在表面上有起伏）——这类噪声不需要"知道"模型长什么样。
**不要做**：需要"知道形状"的细节。这类只能人工在图像编辑器里画。

## 3. 标准流程（七步）

```
① 侦察   列出所有相关形状 + 每个形状的全部贴图槽 + 每个槽的实际文件
② 建组   按 §1 分组，显式写出【包含清单】和【排除清单】
③ 测基准 从"看着对"的那件读出【全部】参数，不是挑几个
④ 备份   针对性备份：全部 NIF + 本次会被修改的贴图（不要全量备份）
⑤ 预演   打印"将要改哪些文件/形状/从什么值到什么值" + 合理性检查
⑥ 写入   按组施加参数
⑦ 验证   换一个对象重新打开回读 + 与基准逐项对比 + 核对排除项未被碰
```

### 3.1 为什么"测基准"要读全部参数

只比较 2-3 个参数会**漏掉真正的差异源**。
本工程中，一个"看起来一样"的表面问题，真正的差异出在一个**没被比较的**参数上；而另一个问题出在**反射球文件**不同，不在任何数值上。

**做法**：dump 出这个形状的**全部**可用属性（含贴图槽的完整路径），与基准逐行 diff。

### 3.2 预演（dry-run）要检查什么

```
✓ 文件数量对不对（是不是只动了该动的）
✓ 形状数量对不对
✓ 每个形状的【分组判定】是否合理（尤其：有没有"皮肤/身体/参考体"混进来）
✓ 目标值是否落在合理区间（和基准同一量级）
✓ 是否涉及共享贴图（涉及就必须改方案 -> 用副本）
```

**本工程的 dry-run 拦下过三种事故**（都发生在真正写入之前）：
1. 一批本不该被碰的部件因为**同名形状**被纳入
2. 皮肤/身体形状因为**判据太宽**被纳入
3. 两个风格组因为**共用贴图**被一起改

### 3.3 验证必须换对象

```
✗ 同一个 NifFile 对象读回来 —— 会被缓存骗过
✓ 重新 NifFile(path) 打开再读
✓ 最好再和一个"基准形状"逐项对比，而不是只看有没有值
```

## 4. 纠错协议

把本工程踩过的坑抽象成**可执行的检查项**，每批作业前过一遍。

### 4.1 动作前

| 检查 | 症状 | 对策 |
|---|---|---|
| **同名不同内容** | 同一个文件名在多个目录下，内容不同 | 一律用**完整相对路径**，禁止只用文件名匹配 |
| **只读派生属性** | 某属性赋值不报错，但文件里没变 | 写入后**换对象回读**；不生效就找底层字段 |
| **共享资源** | 贴图/网格被多个部件引用 | 改前列引用者；超范围就建副本 |
| **作用域判据过宽** | 用"贴图名/贴图关键词"分组 | 改用**文件名或显式清单**（同一贴图可能被两组共用） |
| **排除项混入** | 皮肤/身体/参考体被当成服装 | 每批都写**排除清单**，验证时逐条核对 |

### 4.2 验证工具本身也要验证

**这是最隐蔽的一类错误**：验证脚本自己有 bug，于是给出完全错误的结论，让人在错误的方向上反复返工。

本工程连续三次被同一个 bug 误导：
```
把"改前/改后"的图转换到两个固定目录 -> 不同目录下【同名文件互相覆盖】
-> 取到的对比图其实是同一个文件 -> "改前和改后一模一样"
-> 误判为"改动没生效"
```

**对策**：
```
✓ 每个输入文件的中间产物用【唯一文件名】（含完整路径的哈希/展平）
✓ 或者：每个文件一个独立目录
✓ 结论反常时，先怀疑验证工具，再怀疑改动本身
```

### 4.3 视觉判断 vs 数字判断

```
能算就不要看 —— 预览渲染受软件自身光照限制，未必反映真实效果
必须看图时 —— 裁剪区要对着【改动发生的区域】，否则"前后一样"是必然的
```

### 4.4 作用域事故的恢复顺序

```
1. 立刻停止后续写入
2. 从【本批开始前】的备份还原全部 NIF
3. 用更精确的判据重做（把"关键词匹配"换成"文件名/显式清单"）
4. 验证时把【排除项】逐条列出来看
```

## 5. 查证协议：先查文档，再动手

### 5.1 顺序

```
① 官方文档 / 项目 wiki      <- 永远从这里开始
② 源码
③ 社区（论坛、issue、Nexus 文章）
④ 反向工程（读二进制/试位）  <- 最后手段
```

### 5.2 一个真实案例

**问题**：需要打开一个着色器标志位。

**错误做法**（浪费了多轮）：从"已经开着该标志的样本"反推标志位。
```
失败原因：
  - 该字段高位是 CRC 校验，会随标志组合变化 -> 反推出来的"候选位"其实是 CRC 位
  - 样本数量少，且不同样本可能来自完全不同的着色器配置
  - 试着写位 -> 写得进去但语义不对 -> 验证器读出来还是 False
```

**正确做法**（10 秒解决）：查库的官方 wiki。
```
wiki 里有完整的标志位常量表：
  <标志名> = 1 << 21        <- 在【第二个标志字段】里，不是第一个 ✗
```

**教训**：**"反推"看起来聪明，实际上慢且不可靠；文档才是最快的路。**

### 5.3 检索关键词模板

```
<库名> <属性名> wiki
<库名> <格式名> docs
<格式名> <字段名> specification
<引擎> <着色器/材质> flag <标志语义>
```

### 5.4 查到的结论要落盘

```
✓ 写进文档，注明来源链接
✓ 记录"在哪个字段/哪个位/取值范围"
✓ 记录"是否被当前渲染器响应"——这一项文档通常不写，必须实测
```

## 6. 备份与回退

### 6.1 备份策略

```
针对性备份：只备【本次会被改的文件】+ 全部 NIF
不做全量备份：一套服装的贴图动辄几百 MB，全量备份会迅速堆积
命名带语义：目录名写清"这一步做了什么"，方便精确回退到某一层
```

### 6.2 回退 = 三件事

```
1. 还原 NIF
2. 还原被原地修改的贴图
3. 删除本次【新建】的贴图（否则它们会变成孤儿文件）
```

### 6.3 中间态备份用完即删

```
一个持续数小时的工程，每个中间步骤都留备份 -> 轻易累积数 GB
规则：某一步被确认废弃后，它的备份立刻删除；
      只保留【原始状态】和【最近一个可用状态】
```

### 6.4 回退粒度要能说清

回退时明确告诉用户：**退到了哪一层**、这一层**保留了什么**、**退掉了什么**。
含糊的"已回退"没有价值。

## 7. 交付前自检清单

```
[ ] 分组是否显式写出（包含清单 + 排除清单）
[ ] 组内参数是否完全一致（含反射球、高光色、标志位，不只是数值）
[ ] 组间参数是否有明确区分
[ ] 每个被改的贴图，是否确认过"没有超出作用域的引用者"
[ ] 所有写入是否都用【新对象回读】验证过
[ ] 排除项（皮肤/身体/参考体/其它组）是否逐条核对未被动
[ ] 新生成的贴图：格式（尺寸/mip/编码）是否与原有一致
[ ] 新建的贴图是否都真的被引用了（没有孤儿文件）
[ ] 备份是否可用（能否真的还原）
[ ] 是否有"文档里查得到、但没实测"的假设 —— 明确标注出来交给用户实测
[ ] 预览图/统计脚本本身是否可信（唯一文件名 / 裁剪区对着改动处）
[ ] 回退路径是否一句话能说清
```

## 8. 三条最贵的经验

**① 作用域比数值重要。**
分组错了、判据宽了、共享资源没查，改得再准也是灾难。

**② 验证工具要先被验证。**
本工程最长的返工不是改错，而是**被自己的验证脚本骗了**。

**③ 文档优先，不要反推。**
需要知道"某个位/某个字段"的时候，先搜官方 wiki。
反推看起来聪明，实际慢、不可靠、且容易自我确认。
